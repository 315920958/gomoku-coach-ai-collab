# 项目结构总览

> 从高处看 gomoku-coach 系统由哪些部分构成、彼此怎么调用、将来会长成什么样。

## 系统定位

**gomoku-coach** = 五子棋教练系统。核心价值：把一个**胜率计算引擎**给的冷冰冰数字，翻译成人能听懂的「现在该下哪、该防哪」的建议。

## 四层调用关系

```
[未来的表现层]   网页前端（面向用户）
      │
      ▼
[未来的后端]     调取引擎项目的服务
      │
      ▼
[gomoku-coach-engine]   解说引擎（当前唯一代码项目）
      │                      把胜率翻译为人话
      ▼
[胜率计算引擎]   底层、真正算胜率的引擎（外部 / 已有，未入仓）
```

注意：**「引擎」在这个系统里出现两次，但指两样东西**。

- `gomoku-coach-engine` 是「解说引擎」——它自己是一个项目 / 服务。
- 「胜率计算引擎」是它底下依赖的、真正去算胜率的那个（外部的）。

一个引擎调用另一个引擎很正常，但文档与对话中必须点清是哪一层，避免混淆（详见 `spec/02-术语表.md`）。

## 现有仓库

| 仓库 | 类型 | 作用 |
|---|---|---|
| `gomoku-coach-ai-collab` | 文档仓（本仓） | 定规范、做通讯、描述整体结构 |
| `gomoku-coach-engine` | 代码仓 | 解说引擎：调拉菲 CLI → Node.js 硬性指标 → skill 路由与讲解 |

## 未来可能新增

- **表现层（前端）**：向用户展示教练建议的界面。
- **后端**：专门调取 `gomoku-coach-engine` 的服务层。
- 代码项目不限于一个，未来可能再有多个；其命名与职责届时在 `decisions/` 记录。

## 解说引擎的探索方式

`gomoku-coach-engine` 当前不按最终实现假设预切代码子目录，而是积累可回放的案例和实验。其稳定调用链为：局面 → 拉菲命令行完整输出 → Node.js 生成硬性指标 → 总入口 skill 选择限定分支 → 分支 skill 输出讲解。

每个案例在代码仓的 `cases/` 与 `experiments/` 中各占一个同编号目录。`cases/` 保存原始局面、拉菲完整分析数据和人工讲解；`experiments/` 保存硬性指标、所属大类型和 AI 生成讲解。人工讲解以“多张图、每图多段且按点击顺序展示”保存，整组段落看完后才进入下一图。

## 代码项目分支规范

所有**代码项目**（当前 `gomoku-coach-engine`，未来若有更多）统一采用三套长期分支：

| 分支 | 用途 |
|---|---|
| `develop` | 开发集成分支，日常开发与功能合并在此进行 |
| `test` | 测试分支，用于测试环境部署与验证 |
| `production` | 生产分支，对应线上稳定版本 |

约定：
- 三分支均为仓库长期分支；新建代码项目时即建立，并推送到远程。
- 初始代码落在 `develop`；`test` / `production` 从 `develop` 拉出，初始指向同一基线。
- 本约定已在 `gomoku-coach-engine` 落地：`develop` / `test` / `production` 均已建立并推送。
- 文档仓（ai-collab）不属于代码项目，不强制此三分支结构。
