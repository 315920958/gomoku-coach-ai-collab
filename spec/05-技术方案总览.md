# 技术方案总览

> 本文汇总 `gomoku-coach-engine` 接入「拉菲（rapfi）」胜率计算引擎的全部技术方案，是调用入口代码的权威说明。`src/rapfi/` 下的代码注释与本文保持一致，二者冲突时以本文为准。
>
> 读者先读 `spec/01-项目结构总览.md`（层级与调用关系）与 `spec/02-术语表.md`（名词定义），再读本篇实现细节。

---

## 1. 引擎层级与稳定调用链

「此引擎非彼引擎」是项目核心命名约定（详见 `spec/02-术语表.md`）：

- **解说引擎** = `gomoku-coach-engine`：把胜率翻译成人话的项目，当前唯一代码项目。
- **胜率计算引擎（拉菲 / rapfi）** = 它底下调用的、真正算胜率的外部程序，通过**命令行（CLI）**调用，不入库。

engine 内部稳定调用链（已与用户对齐）：

```
局面（天元棋谱）
   │  调拉菲 CLI（子进程）
   ▼
[拉菲 rapfi]  输出完整分析数据（胜率 / 威胁 / 走子线 / 各候选手指标）
   │
   ▼
[Node.js 分析层]  提炼硬性指标（重点攻坚点、必防/必抢关键手）
   │
   ▼
[总入口 skill] 选限定讲解分支 → [分支 skill] 输出面向用户的讲解
```

本篇聚焦**前半段**：Node.js 如何调起拉菲、解析其输出，并对调用方保持「天元坐标系」契约。后半段（skill 路由与讲解）见后续阶段文档。

## 2. 拉菲调用协议（命令序列，逐字照搬参考项目）

调用方式：Node.js 用 `child_process.spawn` 起拉菲子进程，通过 **stdin 下发命令、stdout 按行读取结果**。以下命令序列与坐标换算**从 `jiang5t-ai-invoke-rapfi` 项目逐字照搬，不得改动**。

### 2.1 进程生命周期命令

| 阶段 | 下发内容 | 说明 |
|---|---|---|
| 启动参数 | `--config=config_nonnue.toml`（仅 `type='nonnue'` 时附加，否则不传，用默认 `config.toml`） | 相对二进制所在目录查找 |
| `begin()` | `INFO timeout_match 0` <br> `INFO timeout_turn <timeout>` <br> `INFO show_detail 2` | 设置整局/单手超时与详细输出模式；下发后等两行就绪回显 |
| `setLine(line)` | `start <line>` | 设置棋盘路数（如 19/15），等回 `OK` |
| `block(coord, part)` | `yxblock` + 每行 `<X>,<Y>,<color>` + `DONE` | 预设子 / 禁手（坐标已是拉菲坐标，见 §3） |
| `think(code, bestn)` | `yxboard` + 每行 `<X>,<Y>,<color>` + `DONE` + `yxnbest <bestn>` | 下发整盘局面并请求前 `bestn` 手；等回一行 `x,y`（拉菲坐标） |
| `end()` | `END` | 结束进程 |

### 2.2 输出解析字段（`INFO ...` 行）

`think` 的回显中每行形如 `INFO <字段> <值...>`，需解析的关键字段：

| 字段 | 含义 | 解析 |
|---|---|---|
| `PV` | 走子线（字母+数字串，见 §3.3） | 转成天元坐标序列 |
| `DEPTH` | 搜索深度 | 整数 |
| `SELDEPTH` | 自选深度 | 整数 |
| `NODES` / `TOTALNODES` | 节点数 | 整数 |
| `TOTALTIME` | 总耗时(ms) | 整数 |
| `SPEED` | 速度(节点/秒) | 整数 |
| `EVAL` | 评估值 | 见 §2.3 |
| `BESTLINE` | 最佳走子线（同 PV 解析） | 转天元坐标 |

### 2.3 评估值（`EVAL`）语义

- 以 `+M` 开头 → 必胜（`sure:1, sureWin:true, eval:MAX`）
- 以 `-M` 开头 → 必败（`sure:-1, sureLose:true, eval:-MAX`）
- 否则 → 普通数值（`sure:0, eval:数字`）

### 2.4 结果聚合

`think` 返回结构：`{ answer:{x,y}(天元), info, full, moves }`

- `answer`：拉菲回的 `x,y` 经 §3.2 转回天元坐标，即「最佳一手」。
- `moves`：所有候选首手（去重）及其对应 `infos`（按深度排序）。
- `info`：`moves` 中每手取最优 `infos` 后，按 `(depth,pv)` 排序取前 `bestn` 手。
- `full`：原始解析明细（`debug=true` 时保留，默认剔除）。

## 3. 坐标系：天元 ↔ 拉菲

**外部契约全程使用「天元坐标系」**（入参棋谱、出参 `answer` 都是天元坐标）；内部与拉菲通信时换算为拉菲坐标。

### 3.1 半盘偏移

```
half = line >> 1      // 19 路 → 9；15 路 → 7
```

### 3.2 整盘坐标换算

- 天元 `(x, y)` → 拉菲：`[x + half, half - y, color]`
- 拉菲 `(x, y)` → 天元：`{ x: x - half, y: half - y }`

（`color`：黑=1 / 白=2，由落子奇偶性决定，参考项目用 `parts=[1,2]` 交替）

### 3.3 走子线（PV / BESTLINE）解析

PV 串是「字母+数字」交替（如 `K11 M13 ...`），每个落点解析：

```
x = 字母.charCodeAt(0) - 65 - half
y = half - 数字 + 1
```

> 整盘坐标与走子线坐标使用**两套不同公式**，照搬参考项目，不可混用。

### 3.4 棋谱串格式

- 入参 `code`：`"x_y;x_y;x_y;..."` 用 `;` 分隔每手，每手 `x_y` 用 `_` 分隔；可带 `|||` 后缀（如禁手/额外信息），解析时只取 `|||` 之前部分。
- 出参 `answer`：`{x, y}` 天元坐标。

## 4. 外部调用契约（`analyze` 函数）

入口封装在 `src/rapfi/analyze.js`，对调用方暴露一个薄函数：

```js
analyze(code, {
  line = 19,        // 棋盘路数
  bestn = 3,        // 返回前 N 手最佳
  timeout = 200,    // 每手思考超时(ms)
  blocks,           // 预设/禁手坐标串（天元，格式同 code）
  type = 0,         // 0=默认 config；'nonnue'=config_nonnue.toml
  path,             // 强制指定 rapfi 可执行文件完整路径（覆盖平台自动选择）
  debug = false,    // true 时保留 full 明细
})
// → { answer:{x,y}(天元), info, full, moves, success:true }
```

- 内部流程：`start → begin → setLine → (block) → think → end`，全程对调用方透明换算坐标。
- 保留 `RapfiInvoker` 类，细粒度控制（start/begin/setLine/think/block/end/exit）仍可单独调用。

## 5. 多平台二进制方案

不同协作者操作系统不同（macOS / Windows / 未来可能 Linux），二进制分平台存放：

```
gomoku-coach-engine/rapfi/
├── windows/   # Windows 协作者：直接复用参考项目全套（已入库）
│   ├── pbrain-rapfi_avx2.exe
│   ├── *.dll（libgcc_s_seh-1 / libstdc++-6 / libwinpthread-1 / tbb）
│   ├── config.toml / config_nonnue.toml
│   ├── model210901-e05000.bin
│   └── mix6*.bin.lz4（5 个权重文件）
├── macos/     # macOS 协作者：从 dhbloo/rapfi 源码构建（见任务卡）
│   ├── pbrain-rapfi_avx2（无扩展名，USE_NEON=ON 构建）
│   └── 模型与 config（同 windows，跨平台通用，直接复制）
└── linux/     # 占位，暂未构建
```

### 5.1 平台自动选择

`analyze.js` 按 `process.platform` 自动选目录与文件名：

| platform | 目录 | 二进制名 |
|---|---|---|
| `win32` | `rapfi/windows` | `pbrain-rapfi_avx2.exe` |
| `darwin` | `rapfi/macos` | `pbrain-rapfi_avx2` |
| `linux` | `rapfi/linux` | `pbrain-rapfi_avx2` |

### 5.2 cwd 设置（关键）

`spawn` 子进程时把 **cwd 设为二进制所在目录**。原因：`config.toml` 内 `binary_file` / `weight_file` 均为**相对文件名**，拉菲在 cwd 下查找；设 cwd 后 Windows / macOS 各自跑自己目录即可找到模型，无需任何路径改动。

### 5.3 覆盖机制

- 环境变量 `RAPFI_PATH`：强制指定二进制完整路径（cwd 取其目录）。
- `opts.path`：同 `RAPFI_PATH`，优先级更高（单次调用覆盖）。

### 5.4 模型与权重

- 跨平台通用，不区分系统；每个平台目录**自包含**模型 + config（直接复制同一份）。
- 二进制与权重均**提交进仓库**（用户决定），clone 即可跑，无需额外下载。

## 6. 代码文件映射与迁移说明

代码位于 `gomoku-coach-engine/src/rapfi/`：

| 文件 | 职责 | 来源 |
|---|---|---|
| `cmd-invoker.js` | 子进程通信层：spawn、按行缓冲 stdout、按 predicate 等目标行、写 stdin、退出杀进程（含 `cwd` 支持） | 从 `jiang5t-ai-invoke-rapfi/CmdInvoker.js` 迁移为 ESM |
| `rapfi-invoker.js` | 调用核心：坐标换算 + 命令序列 + 输出解析（保留 `RapfiInvoker` 类） | 从 `RapfiInvoker.js` 迁移为 ESM |
| `analyze.js` | 本地一次性入口封装 + 多平台选择 | 新增（薄封装，保留类） |

### 6.1 迁移取舍（相对参考项目）

- **保留**：坐标换算、命令序列、输出解析全部逐字照搬，逻辑不变。
- **改写**：`require` → `import/export`（ESM）；ESM 严格模式下 `eval` 不能作形参名，改为 `acc`（逻辑一致）。
- **丢弃**：HTTP 层（`app.js` / `GeneralController.js`）、`dragonli-*` 三个 Express 依赖、并发限制 `MAX_CONCURRENT_COUNT`（均为多请求服务设计，本地单次调用不需要）。
- **依赖**：不再需要 `q` 库（用原生 `Promise` 替代）。

## 8. 风险与待决

| 风险 | 说明 | 对策 |
|---|---|---|
| macOS Gatekeeper 拦截未签名二进制 | 第三方二进制可能被「无法验证开发者」拦截 | `xattr -d com.apple.quarantine <bin>`；必要时 `chmod +x` |
| Apple Silicon NEON 构建前置 | 需 `cmake` 与编译器；官方用 `USE_NEON=ON` | 构建前装 `brew install cmake` |
| 权重子模块体积 | `dhbloo/rapfi` 的 `Networks` 子模块较大，克隆慢 | 已用 `--recurse-submodules`；或仅复制参考项目 windows 目录的模型（跨平台通用），不依赖源码子模块 |
| 二进制进仓使仓库变大 | 各平台目录合计数百 MB | 用户已决定「提交进仓库」，接受体积；后续若需可用 Git LFS |
