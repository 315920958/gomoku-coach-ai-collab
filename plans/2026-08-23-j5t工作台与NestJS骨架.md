## 1. 统一命名：j5t 格式

**j5t 格式**指以天元坐标为基础、使用 `|||` 分段的完整局面记录。

```text
落子|||圈|||热点|||进攻方|||字母标记|||线|||自动线方
```

- 第 0 段是基础棋谱，可直接传给 Rapfi；
- 后续段保留人工标注和界面表达信息；
- 所有 `x_y` 均为天元坐标；
- 引擎项目的 `parseTianyuanRecord()` / `generateTianyuanRecord()` 是 j5t 的程序入口。

## 2. j5t 导入与自有 JSON 格式

j5t 是导入和来源追溯格式，不作为案例内部的唯一标准。导入后必须归一化为项目自己的 JSON：

```json
{
  "format": "gomoku-coach-position",
  "version": 1,
  "board": { "line": 19, "coordinateSystem": "tianyuan" },
  "moves": [{ "x": 0, "y": 0 }],
  "annotations": {
    "circles": [{ "at": { "x": -2, "y": 0 }, "color": "#ff0000", "size": 18, "type": "solid" }],
    "lines": [{ "from": { "x": -3, "y": 0 }, "to": { "x": 1, "y": 0 }, "deg": 0, "color": "#00aa00", "width": 2 }]
  },
  "source": { "j5t": "原始导入内容" }
}
```

`hotInfo` 是 aiBase 计算结果，不进入自有 JSON；j5t 的攻击方、自动线方和字母标记也暂不进入自有 JSON。原 j5t 只放在 `source.j5t` 中，用于追溯、重新导入和未来兼容。

## 3. 线的两层表示

j5t 原始格式中，线按经过的每个格子记录；这是导入层格式，原始文本保留在 `source.j5t`，避免丢失来源信息。

在展示给大模型、生成硬性指标或人工讲解上下文时，额外归并为**线段语义格式**：

```js
{
  from: { x, y },
  to: { x, y },
  deg: '45',
  color: '#0f0',
  width: 2,
}
```

仅有起点不足以表达线的范围，因此采用“起点 + 终点”；方向、颜色和粗细保留。归并原则：同 `deg/color/width` 且在该方向上相邻的格子合成一条线段；不连续部分保持为多条线段。规范 JSON 只保存归并后的 `annotations.lines`，避免两份可编辑数据发生不一致。

## 4. case 与人工讲解数据

每个 case 是一个独立 JSON 文档；每张“图”持有自己的、可独立编辑的局面 JSON 和按顺序展示的文字段：

```json
{
  "format": "gomoku-coach-case",
  "version": 1,
  "id": "case-...",
  "title": "未命名案例",
  "frames": [
    {
      "id": "frame-...",
      "position": { "...": "gomoku-coach-position" },
      "paragraphs": ["第一段讲解", "第二段讲解"]
    }
  ]
}
```

复制“图”会复制当时的完整局面，不会与其他图联动；因此用户可以在后续图上继续增加棋子、圈或线。

## 5. 用户工作台建议

目标不是一次性自动讲解，而是让用户积累“局面 → 人工讲解 → 可复盘信号”的案例。

```text
导入 j5t
  → 校验并绘制棋盘
  → 用户添加/确认标注和焦点
  → 分图、分段写人工讲解
  → 保存为案例
  → 后续与 AI 讨论：提炼硬性指标和讲解路径
```

建议首版界面三栏：

| 区域 | 内容 | 用户操作 |
|---|---|---|
| 左栏：局面输入 | 案例标题、粘贴 j5t、解析状态、已保存案例 | 粘贴、校验、保存、载入 |
| 中栏：棋盘 | 天元坐标轴、黑白落子、圈、线 | 落子、后退、画线、画圈 |
| 右栏：讲解工作区 | 当前案例的“图”和每图的多段文字 | 新建图快照、逐段撰写、调整点击展示顺序、标记该段关注的点/线 |

### 5.1 粘贴与绘制

1. 用户粘贴 j5t；
2. 前端即时调用 j5t 解析器，显示具体段/坐标错误；
3. 解析成功即绘制棋盘，边缘显示 x/y 天元坐标；
4. Rapfi 只收到第 0 段，标注保留在案例中。

### 5.2 棋谱编辑快捷键

| 操作 | 行为 |
|---|---|
| 普通模式（`Esc` 或 `0`） | 点击空位按落子顺序增加黑/白棋；“后退”删除最后一手 |
| `1`：画线模式 | 第一次点击记录起点并显示三角；第二次点击记录终点并显示三角。仅水平、垂直、`+45°`、`-45°` 有效；不合格线不写入 |
| `2`：画圈模式 | 点击空位增加圈；点击已有圈移除圈 |
| 字母 | 暂不实现 |

画线成功后记录 `from/to/deg/color/width`；`deg` 与端点必须一致。线段端点三角仅在正在画线时展示，不作为最终标注保存。

### 5.3 人工讲解的最小单元

一个案例可以含多张图。每张图存：

- 对应的 j5t 快照（可只展示至某手）；
- 用户选中的焦点点、圈和线段；
- 依次点击出现的若干讲解段；
- 关联的 Rapfi 原始分析及后续硬性指标版本。

界面应让用户先“新增图”，再逐段写文字；不要把整局讲解压进单一长文本框。

## 6. NestJS 项目边界

在工作区根目录建立独立项目 `gomoku-coach-app/`：

```text
gomoku-coach-app/
├── src/             # NestJS API
├── public/          # 暂时的前端静态入口，由 NestJS 同域托管
├── test/
└── package.json
```

NestJS 同域托管 `public/`，并提供：

- `POST /api/j5t/parse`：j5t → 自有局面 JSON；
- `GET /api/cases`、`GET /api/cases/:id`、`POST /api/cases`：本地 case JSON 的文件持久化。

首版仍不引入 React/Vue 或数据库；case 使用项目本地 `data/cases/` 的 JSON 文件保存，后续再根据实际协作需要替换存储层。

### 6.1 本轮调整：编辑目录与发布流程

`data/cases/` 不再是平铺的案例文件，而是编辑目录的集合：

```text
data/cases/
├── main/
│   ├── index.json                 # 已确认案例：编号、简述、标题
│   └── 000001/
│       ├── case.json              # 可继续修改的最终案例
│       └── rapfi.json             # 创建时的完整 Rapfi 原始结论
└── 编辑者姓名/
    ├── index.json                 # 此编辑目录仍在编辑的案例索引
    └── 000002/
        ├── case.json
        └── rapfi.json
```

- 首次进入不展示案例列表，必须先选择或新建一个编辑目录；选择写入浏览器 `localStorage`，以后自动打开该目录，但界面始终允许切换。
- 在某编辑目录创建案例时，系统扫描现有编号后分配下一个六位十进制编号（`000001` 起）；创建表单只有 j5t 棋谱和可空简述。左侧列表显示简述（过长省略），否则显示编号。
- 创建操作调用本地 Rapfi：`bestN=5`、单手时间 `5000ms`；完整返回结果写入同编号目录的 `rapfi.json`。
- 从个人目录发布时，先把整个编号目录移动到 `main/`，再更新两个索引，最后删除个人索引中的该记录。移动成功前绝不删除个人原件；发布后个人目录不再保留该案例。
- `main` 的案例仍可修改。首版的 Rapfi 面板显示 5 个候选点的天元坐标、胜率和最佳线路长度。

## 9. 已完成骨架的实际实现与验收

已创建工作区根目录下的独立项目：`gomoku-coach-app/`。

- 后端：NestJS 11；
- 前端：由 `@nestjs/platform-express` 的静态目录能力同域托管 `public/`，未引入 React/Vue；
- 健康接口：`GET /api/health`，返回 `{ "status": "ok", "service": "gomoku-coach-app" }`；
- 前端入口：`GET /`，是可操作的三栏工作台：导入、棋图编辑和逐图逐段讲解；
- j5t 归一化：`POST /api/j5t/parse`。保留落子、圈和归并后的线段，忽略 `hotInfo`、进攻方、字母和自动线方，原文保存至 `source.j5t`；
- 案例持久化：`GET /api/cases`、`GET /api/cases/:id`、`POST /api/cases`；保存位置为 `gomoku-coach-app/data/cases/`，该目录的真实案例文件默认不纳入 Git；
- 编辑：`Esc`/`0` 落子，`1` 两点画横/竖/±45°线，`2` 画圈；后退只撤销最后一手；新增图会复制当前棋图；
- 环境：实测 Node.js `v26.0.0`、npm `11.12.1`；NestJS 11 运行环境应使用 Node.js 20 或更高版本。

启动：

```bash
cd gomoku-coach-app
npm install
npm run start:dev
```

实际验收已执行并通过：

```bash

npm run test:e2e -- --runInBand
PORT=43001 npm run start
curl http://127.0.0.1:43001/api/health

```

实际验证包括构建、全部单元/e2e 测试，以及真实 HTTP 的 j5t 解析和案例保存；解析结果确认不含 `hotInfo`，格子级的三点横线正确归并为一条 `from/to` 线段。验证服务已停止。

Rapfi 调用和大模型调用仍不在本轮范围内；字母标注、热点与复杂的棋谱编辑历史也留待后续按案例积累推进。
